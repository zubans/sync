# Календарь

Календари и события хранятся на сервере sync. Работать с ними можно двумя способами:
- через REST API по токену — из любого клиента;
- на Android — через календарь устройства: календари sync видны в нём под аккаунтом приложения.

## Модель

- **`Calendar`** — календарь пользователя: название, цвет `#RRGGBB`, отметка «семья» (`familyShared`), «Поделиться с» (`sharedWith`, таблица `calendar_share`) и счётчик ревизий.
  - Кому виден календарь (`Calendar::isVisibleTo`): личный — только владельцу; с отметкой «семья» — всем членам семьи владельца; «Поделиться с» — выбранным членам семьи владельца (календарь Сержика — маме, но не всей семье). Делиться можно только внутри семьи: чужого человека админка не примет, а вышедший из семьи (владелец или тот, с кем поделились) теряет доступ, даже если остался в списке.
  - Если у пользователя нет своих календарей, сервер при первом `GET /api/calendars` создаёт «Личный». Так устройству всегда есть куда писать.
  - Семейный и поделённый календарь видят и правят события те, кому он открыт. Переименовать, перекрасить или удалить его может только владелец.
  - Вышел владелец (или член семьи) из семьи — календарь для остальных пропадает, с устройств тоже.
- **`CalendarEvent`** — событие: название, начало и конец, «весь день», место, описание, свой цвет, правило повторения `rrule` (RFC 5545, без префикса `RRULE:`).
  - Время хранится в UTC.
  - Событие на весь день хранится с полуночи UTC первого дня до полуночи дня после последнего, конец не включается. Так же события хранит Android.
  - Повторения сервер хранит как есть и не раскрывает.
  - Удалённое событие остаётся «надгробием» (`deleted`), чтобы удаление дошло до всех устройств.

## Ревизии и одновременные правки

Каждая правка события получает следующую ревизию своего календаря, как в хранилище паролей.

- **Синхронизация.** Клиент запоминает ревизию календаря и забирает изменения с неё: `GET /api/calendars/{id}/events?since=N`. В ответе есть и удалённые события.
- **Правка** приходит с `baseRevision` — ревизией, от которой её делали.
  - Если событие с тех пор изменили, правка не применяется. Клиент получает `conflict` и текущую версию.
  - Создание с уже занятым `id` — тоже `conflict`: чужое событие не затирается.
- **Пакет правок** — `POST /api/calendars/{id}/changes` (до 500 правок). Результат по каждой:
  - `ok` — с ревизией и сохранённым событием;
  - `conflict` — с текущей версией (`current`);
  - `rejected` — например, событие из другого календаря или превышен лимит в 20 000 событий.
- **Разовые правки:**
  - `PUT /api/events/{id}` без `baseRevision` применяется к текущей версии, с ним — только если событие не меняли (иначе `409` и `current`);
  - `DELETE /api/events/{id}?baseRevision=` удаляет так же.

## API

Все запросы — с `Authorization: Bearer <token>`.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/calendars` | календари: свои, семейные календари членов семьи и те, которыми поделились. Поля: `id`, `name`, `color`, `familyShared`, `access` (`own` — свой, `family` — семейный, `shared` — поделились), `owner`, `mine`, `revision` |
| POST | `/api/calendars` | создать: `{name, color?, familyShared?}` |
| PUT | `/api/calendars/{id}` | изменить (только владелец) |
| DELETE | `/api/calendars/{id}` | удалить вместе с событиями (только владелец) |
| GET | `/api/calendars/{id}/events?since=N` | изменения после ревизии N: `{revision, events}` |
| POST | `/api/calendars/{id}/changes` | пакет правок: `{changes: [{id, baseRevision?, deleted?, title, start, end, allDay, …}]}` |
| POST | `/api/calendars/{id}/events` | создать событие (`id` можно передать свой, UUID) |
| GET | `/api/events?from=&to=&calendar=` | события, пересекающиеся с периодом `[from, to)`, не длиннее 366 дней |
| GET, PUT, DELETE | `/api/events/{id}` | событие, правка, удаление |

**Время.**
- На входе — ISO 8601 со смещением: `2026-10-10T15:00:00+03:00` или `…Z`. Время без смещения отклоняется: непонятно, в каком оно поясе.
- В ответах время — в UTC.
- Для `"allDay": true` начало и конец — даты `YYYY-MM-DD`, конец позже начала.
- `from`/`to` в периоде — дата или время.

**Повторения.** Повторяющиеся события период не раскрывает. Отдаются все, что начались до конца периода; вхождения клиент считает по `rrule`.

**Ошибки.**
- Чужой или несуществующий календарь и событие — `404`.
- Попытка изменить чужой календарь — `403`.
- Невалидные данные — `422`.

## Примеры запросов

Токен выдаёт вход: `POST /api/auth/login` с `{email, password}` → `{token}`. Дальше каждый запрос — с заголовком `Authorization: Bearer <token>`.

**Календари**

```http

→ 200 {"calendars": [
    {"id": "01a12…", "name": "Личный", "color": "#4285F4", "familyShared": false,
     "owner": "anna@example.com", "mine": true, "revision": 3},
    {"id": "01a13…", "name": "Семья", "color": "#34A853", "familyShared": true,
     "owner": "boris@example.com", "mine": false, "revision": 12}]}

POST /api/calendars
{"name": "Работа", "color": "#EA4335", "familyShared": false}
→ 201 {"id": "01a14…", "name": "Работа", …}
```

**Событие со временем и на весь день**

```http
POST /api/calendars/01a12…/events

 "location": "Zoom", "description": "Обсудить календарь"}

       "allDay": false, "location": "Zoom", "description": "Обсудить календарь",
```

**События за период**


**Правка и удаление**

```http

    {"id": "5554c874-…", "status": "ok", "revision": 7, "event": {…}},
    {"id": "01a16…", "status": "conflict", "current": {…}},
    {"id": "01a17…", "status": "ok", "revision": 9, "event": {…}}]}
```

## Android

Календари sync попадают в календарь устройства (`CalendarContract`) под системным аккаунтом приложения (тип `com.example.contactsync`, имя — email). Код — пакет `calendar`.

**Аккаунт** (`CalendarAccount`).
- Создаётся при входе в sync и при запуске приложения. При выходе удаляется, а вместе с ним система удаляет и календари sync с устройства.
- Нужно разрешение на чтение и запись календаря. Его запрашивают экран «Контакты» вместе с разрешением на контакты и главный экран.

**Синхронизация** (`CalendarSyncService` + `CalendarSync`) — SyncAdapter. Система запускает его:
- раз в час;
- после правок в приложении «Календарь»;
- по запросу: после входа, после выдачи разрешения, при возврате на главный экран (не чаще раза в 5 минут).

**Порядок синхронизации.**
1. Список календарей: новые создаются на устройстве, пропавшие удаляются, название и цвет обновляются. Семейный календарь другого человека подписан его email и доступен для правки.
2. Правки с устройства (`DIRTY`, `DELETED`) уходят пакетом. Новое событие получает UUID на устройстве.
3. Изменения сервера с последней ревизии (`CAL_SYNC1` календаря) записываются на устройство. Ревизия события хранится в `SYNC_DATA1`, серверный id — в `_SYNC_ID`.

**Организатор.** Событиям на устройстве записывается организатор — аккаунт sync (`ORGANIZER`) и `GUESTS_CAN_MODIFY=1`: без этого календарные приложения не дают править событие, а в семейном календаре его правят и другие члены семьи. События, записанные прошлыми версиями без организатора, получают его при следующей синхронизации.

**Конфликт** решается в пользу сервера: событие на устройстве переписывается его версией.

**Перевод событий** (`EventMapping`, покрыт тестами):
- событие на весь день — полночь UTC и пояс UTC;
- у повторяющегося на устройстве нет `DTEND`, есть `DURATION` (`P900S`, `P1D`);
- на сервер конец вычисляется из длительности.

**Ограничения первого шага.**
- Исключения повторяющихся событий (изменённое или удалённое одно вхождение, `ORIGINAL_ID`) не синхронизируются.
- Переносить событие между календарями API не умеет.
- Напоминаний нет.

## Админка

- «Календарь → События» — просмотр и удаление. Время показано в UTC. Удаление оставляет «надгробие», и событие пропадает с устройств.
- «Календарь → Календари» — создание (владелец выбирается при создании, потом не меняется), название, цвет, «Семья» и «Поделиться с» — члены семьи владельца, которым открыт календарь. Так подключаются три вида календарей: личный (только владелец), семейный («Семья» — вся семья, например «Зюбан») и календарь одного человека для выбранных членов семьи (календарь Сержика — родителям).
