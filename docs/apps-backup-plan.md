# План: сохранение приложений и их авторизаций

Статус: план, не реализовано.

Цель — зайти в аккаунт на новом телефоне и получить обратно установленные приложения, по возможности уже авторизованными.

## Короткий вывод

| Что | Можно ли | Как |
|---|---|---|
| Список приложений | Да | `PackageManager`, выгрузка на сервер |
| Сами APK (включая split APK) | Да, с оговорками | Файлы из `ApplicationInfo.sourceDir`/`splitSourceDirs` читаются без root |
| Установка на новом телефоне | Да, но каждую установку подтверждает пользователь | `PackageInstaller` + `REQUEST_INSTALL_PACKAGES`; без подтверждений — только в режиме Device Owner |
| Данные и авторизация сторонних приложений | **Нет** в общем случае | Песочница Android запрещает читать чужие данные без root. Есть обходные пути, см. ниже |

## 1. Инвентаризация приложений

Клиент при синхронизации собирает по каждому пакету:

- `packageName`, `versionCode`, `versionName`, `label`, иконку;
- `installerPackageName` (`getInstallSourceInfo`, API 30+) — откуда поставлено: Google Play, другой магазин, вручную;
- SHA-256 сертификата подписи (`GET_SIGNING_CERTIFICATES`);
- размеры и SHA-256 файлов base/split APK;
- признак системного приложения (системные не сохраняем).

Ограничение Android 11+: видны только пакеты из `<queries>` в манифесте. Чтобы видеть все, нужно `QUERY_ALL_PACKAGES`. Google Play пускает его только для узкого круга приложений (бэкап приложений — один из допустимых сценариев, но с проверкой при публикации). Если распространяться вне Play (корпоративно, через MDM), ограничения нет.

Сервер: сущности `AppPackage` (пакет + версия + подпись, общая для всех пользователей) и `UserApp` (что было установлено у пользователя, на каком устройстве, когда видели последний раз). В админке — список приложений пользователя.

## 2. Хранение APK

- **Что грузим.** Base APK и все split APK (`splitSourceDirs`). Без split'ов современные приложения из Play не установятся. OBB-файлы (`Android/obb`) без root недоступны с Android 11 — не сохраняем, игры докачают их сами.
- **Дедупликация.** Храним по содержимому: ключ — SHA-256 файла. Один и тот же WhatsApp той же версии у тысячи пользователей лежит один раз. Клиент сначала шлёт список хэшей, сервер отвечает, каких файлов у него нет, и загружаются только они.
- **Загрузка.** Файлы по 50–300 МБ: загрузка частями с докачкой (tus или S3 multipart через presigned URL), только по Wi-Fi и на зарядке (WorkManager с `setRequiresCharging`, `NetworkType.UNMETERED`). Хранилище — S3-совместимое (MinIO или облако), не диск PHP-сервера.
- **Политика.** По умолчанию не загружаем APK, которые есть в Google Play (`installer = com.android.vending`): на новом телефоне их правильнее поставить из Play по списку (ссылка `market://details?id=...` или восстановление самим Play). Загружаем только приложения не из Play, либо всё — если так решит администратор. Это экономит место и снимает часть юридических рисков.
- **Юридический риск.** Раздача платных и чужих APK другим людям — нарушение лицензий. Файл, загруженный пользователем, отдаём только этому пользователю (дедупликация хранения не означает общего доступа).

## 3. Восстановление на новом устройстве

1. После входа клиент получает список приложений пользователя и показывает экран с галочками: что поставить.
2. Для приложений из Play — открываем карточку в Play (или пользователь полагается на восстановление самого Google).
3. Для сохранённых APK — скачиваем base и split, проверяем SHA-256 и подпись и ставим одной сессией `PackageInstaller` (`createSession` → `openWrite` для каждого файла → `commit`). Система покажет подтверждение на каждое приложение.
4. Если на телефоне уже есть пакет с другой подписью — не ставим: Android откажет, и это защита от подмены.
5. Установка без подтверждений возможна только если наше приложение — Device Owner (корпоративные устройства, настройка через QR при первом включении). Для личных телефонов это не подходит.

Разрешения клиента: `REQUEST_INSTALL_PACKAGES` (пользователь включает «Установка неизвестных приложений» для нашего приложения), `QUERY_ALL_PACKAGES`.

## 4. Данные авторизации сторонних приложений

**Прямо это невозможно.** Токены, cookies и базы приложений лежат в `/data/data/<package>`, доступ туда есть только у самого приложения и у системы. Прочитать их из нашего приложения без root нельзя, и это принципиальная защита Android, а не техническое ограничение, которое можно обойти.

Что реально можно сделать, от более надёжного к менее:

1. **Системный перенос Android.** Google One Backup и «Перенос данных» при настройке нового телефона (кабель или Wi-Fi) переносят данные приложений, которые это разрешили (Auto Backup / `allowBackup`), включая часть сессий. Наше приложение может только подсказать пользователю включить это и проверить статус. Встроиться в этот механизм нельзя.
2. **Стать менеджером паролей (Autofill Service + Credential Manager provider).** Приложение сохраняет логины и пароли и passkeys, которые пользователь вводит в других приложениях, шифрует их ключом пользователя (end-to-end: мастер-пароль, сервер хранит только шифротекст) и хранит на нашем сервере. На новом телефоне вход в каждое приложение — одно касание автозаполнения. Повторный вход всё равно нужен, но без ввода паролей. Это единственный честный и масштабируемый вариант. Большой отдельный продукт: криптография, аудит безопасности, требования Google к Autofill.
3. **Block Store / Credential Manager самих приложений.** Приложения, которые используют Google Block Store, сами восстанавливают токен на новом устройстве. От нас это не зависит.
4. **Device Owner / MDM.** Даже Device Owner не читает данные чужих приложений. Он даёт только тихую установку и managed configurations для корпоративных приложений, которые их поддерживают.
5. **Root / `adb backup`.** `adb backup` устарел и с Android 12 для большинства приложений ничего не сохраняет. Root выходит за рамки массового продукта: ломает SafetyNet/Play Integrity, и банковские приложения перестают работать.

**Рекомендация:** в рамках продукта реализовать пункты 1–3 (список, APK не из Play, установка через `PackageInstaller`). Для авторизаций — отдельным этапом, как менеджер паролей со сквозным шифрованием (вариант 2), и честно сказать пользователю, что сессии банков и мессенджеров перенесёт только системный перенос Android.

## 5. Этапы

1. Инвентаризация: список приложений на сервере и в админке. Небольшая доработка текущей синхронизации.
2. S3-хранилище, дедупликация по хэшу, загрузка APK не из Play по Wi-Fi.
3. Экран восстановления и установка через `PackageInstaller`, проверка подписи.
4. (Отдельный проект) Autofill/Credential provider с E2E-шифрованием.
